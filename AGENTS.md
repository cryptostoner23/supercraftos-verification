# Context.dev integration

The current integration supports source research for the goal **Liquidity arbitrage, MEV infrastructure, and a 1inch Fusion resolver**. It does not implement an operational trading bot, transaction execution, or a profitability guarantee.

- Use the official Python SDK, `context.dev==2.28.0`, through `context_service.py`. `ContextService` is the sole application gateway; do not add direct HTTP clients or SDK calls elsewhere. The runtime uses Python 3.12 and asyncio, with dependencies installed through pip. The optional Rust Tokio worker remains separate.
- Read `CONTEXT_DEV_API_KEY` only on the server through the existing environment loader. Keep credentials out of browser code, source, prompts, logs, generated artifacts, and committed configuration. `.mcp.json` contains environment placeholders only; its AIFlowchart connection reads `AIFLOWCHART_API_KEY`. Never record credential values in this file.
- The verified endpoint is `POST https://api.context.dev/v1/web/search`, called using `AsyncContextDev.web.search`. References: [quickstart](https://docs.context.dev/quickstart), [search guide](https://docs.context.dev/search/overview), and [documentation index](https://docs.context.dev/llms.txt). Cached setup references are `data/context-docs/quickstart.md` and `data/context-docs/search.md`; prefer them when no documentation refresh is requested.
- `resolver_research.py` scopes searches to `github.com`, `business.1inch.com`, and `docs.1inch.io`, with three results by default. Fresh research enables Markdown, requests `max_age_ms=0`, and uses main content only. Preserve request ID, check timestamp, `partial`, cache metadata, and each result's Markdown status. A successful HTTP response does not establish that every page was extracted successfully. Only use Markdown when its status is `SUCCESS`; retain failed statuses. Fresh page retrieval does not establish that a page's claims are current or that a strategy is executable.
- The SDK has `max_retries=0`; the wrapper alone retries transport errors and HTTP 408, 429, or 5xx, with at most three total attempts, jitter, and `Retry-After` support. Backoffs over 60 seconds stop with an explicit error. Do not retry permanent request/authentication failures unchanged or add another retry layer.
- Automated verification must use local transport fixtures: `.venv/bin/python -m unittest -q test_context_service.py`. Do not make paid calls from tests, startup checks, or documentation checks. Running `main.py research` or invoking the MCP tool `research_fusion_resolver` makes a live request and consumes credits; require explicit user intent for additional live calls.

Exactly one real targeted Context.dev search was completed on 2026-10-18, request ID `67731986-2639-4263-87a7-5c47f5f5bfc3`. It returned the official 1inch Intent Swap introduction, Resolver Onboarding Guide, and `1inch/fusion-protocol` repository, all with Markdown status `SUCCESS`; cache metadata reported a miss with age zero. Full response: `data/context-live-response.json`; normalized research: `data/context-resolver-research.json`; concise evidence: `data/context-live-output.json`. The response's `partial` field was null; do not rewrite that as an explicit false value. Reuse this evidence instead of spending credits to repeat verification.

`.mcp.json` defines AIFlowchart and Context.dev remote HTTP servers plus the local SuperCraftOS stdio server. AIFlowchart initialization and tool listing returned HTTP 200 and four tools; see `data/aiflowchart-health.json`. This verifies connection and discovery, not diagram generation. `scripts/claude_with_env.py` loads server-side environment before launching Claude Code; the CLI was absent during verification, so do not claim a Claude session ran. The [NitroStack MCP guide](https://nitrostack.ai/blog/build-chatgpt-app-nitrostack-mcp-guide) is an architectural reference; no NitroStack application was deployed.

# iOS app and keyboard extension

- The iOS app and its custom keyboard extension are compiled on the Bitrise macOS Xcode 27 stack. The pipeline in `bitrise.yml` runs the portable Swift tests, inventories the SDK and type checks the FoundationModels probes, builds the app and the keyboard extension for the simulator, compiles both for the arm64 device architecture, and publishes the artifacts. The verified build history is in `docs/bitrise-integration.md`.
- The Xcode project is generated from `ios_app_dist/ci_xcode/project.yml` with XcodeGen. Never commit a `.xcodeproj`; it carries absolute paths and a merge hostile `project.pbxproj`. The spec is the source of truth for the target graph, the schemes, and the extension embedding.
- The keyboard contract lives in `swift-verification/Sources/ControlCore/KeyboardCatalog.swift`, which is the single source of truth. The Xcode app target, the keyboard extension target, and the Swift Playgrounds bundle all compile that exact file, and `scripts/package_ipad.py` keeps the bundle copy identical. `KeyboardCatalogTests` asserts the tab sequence, the tile set, the two column split, the badge palette, the two word shortcut descriptions, and the action bound to every tile. Change the catalog and the tests together.
- The app ships standalone. The custom keyboard extension is deliberately not embedded by default: embedding it makes the app require a second App ID and, with the App Group enabled, a group on the app's own provisioning profile. The extension target and scheme still exist and CI still builds and verifies them on every push, so it cannot rot. The full configuration is also built and verified in CI by the "Verify the full build with the keyboard embedded" step.
- One spec, two configurations. The keyboard dependency lives in a marked block in `ios_app_dist/ci_xcode/project.yml` that `scripts/xcode_project.py --embed-keyboard` activates. Do not add a second spec file; that would let the two configurations drift.
- The app and optional keyboard use the authenticated gateway. Each keeps its own private access key in its Keychain; the keyboard's connection screen accepts the user's private link. Never restore anonymous `/api/session` access or bake access keys into a build. App Groups are optional and are not required for the free personal build.
- The standalone host targets iOS 17. The optional keyboard targets iOS 26 for FoundationModels; the combined build therefore requires a device supporting iOS 26. Do not link FoundationModels unconditionally into the iOS 17 host.
- Three API shapes break against the current SDK and must not be reintroduced: `SCNScene(mdlAsset:)` does not exist in Swift, `SCNScene(url:options:)` throws, and `UIView.translatesAutoresizingMask` is now `translatesAutoresizingMaskIntoConstraints`.
- The app icon set is generated, not drawn by hand: `scripts/generate_app_icons.py` writes `ios_app_dist/ci_xcode/Assets.xcassets` with the standard library only. Run it instead of editing the PNGs. Every idiom, size and scale slot must stay assigned, because an unassigned child makes Xcode warn and the App Store icon goes missing.
- Installability is part of the contract, not an afterthought. The app needs a compiled app icon, a launch screen, `ITSAppUsesNonExemptEncryption`, and a `PrivacyInfo.xcprivacy`. The keyboard extension needs its own privacy manifest. `scripts/verify_ios_artifacts.py` asserts all of them, and the app and the keyboard are verified as separate bundles because the app no longer embeds the keyboard.
- Free personal installation follows `docs/FREE_APPLE_INSTALL.md`: build on Bitrise, sign/install locally on the Mac with a supported tool, and refresh before the seven-day provisioning expiry. Keep Apple credentials out of scripts, chat and the VPS. An unsigned IPA, a validated profile, a successful install command and a verified physical-device launch are distinct outcomes. TestFlight requires paid membership.
- Default iOS tests use a DEBUG-only authenticated URLProtocol fixture. Test unknown routes fail closed without network fallback. The explicit live workflow is read-only and receives the gateway key as a CI secret. Python live mutation tests require `SUPERCRAFTOS_ALLOW_LIVE_MUTATIONS=1` and an explicit target; never enable these in routine discovery.
- Verification commands: `swift test --package-path swift-verification` for the contract tests, `.venv/bin/python -m unittest -q test_verify_ios_artifacts.py` for the artifact verifier, and `.venv/bin/python scripts/verify_ios_artifacts.py <app.zip>` for a delivered bundle.



# Continuous integration (GitHub Actions)

- `.github/workflows/ci.yml` runs on every push and pull request: the full Python unittest suite (`python -m unittest discover -p "test_*.py"`), the static repository audit (`scripts/audit_repository.py`, which exits non-zero on syntax errors or detected committed secrets), and the Swift contract tests (`swift test --package-path swift-verification`) on Linux.
- The live e2e suite (`test_e2e.py`) skips unless the `SUPERCRAFTOS_E2E_KEY` repository secret is set. Keep every credential in repository secrets or server-side environment; the repository audit now bans committed credentials statically, so a secret in source fails CI.
- Bitrise (`bitrise.yml`) remains the macOS-only Xcode/XcodeGen build, signing and artifact pipeline. GitHub Actions covers only Linux-verifiable checks; do not move iOS builds there.


# Repository sync model (private <-> public verification mirror)

- Two remotes: `origin` = `cryptostoner94/opencode-supercraftos` (private, canonical, full legacy history on `main`) and `public` = `cryptostoner94/supercraftos-verification` (public, fresh single-root history at `853106e`, temporary until the product is fully corrected, tested and verified, then deleted).
- The public repo must NEVER receive the legacy history: it still contains the historical committed access key. The legacy history lives only on `origin` (and in the scratchpad backup `opencode-supercraftos-old-git-20261109`).
- Verified 2026-11-09: the fresh root commit's tree is byte-identical to the private `main` tree (`git diff origin/main` empty after fetch). The bridge commit `66e25bc` on branch `sync` merges `origin/main` into `main`, so both repos' `main` can fast-forward independently without ever exposing legacy commits to the public repo.
- Repeatable sync procedure after every commit on `main`:
  1. `git push` — publishes `main` to `public/main` and triggers Actions CI there.
  2. `git switch sync && git merge main && git push` with remote `origin` and remote branch `main`, then `git switch main` — the private `main` fast-forwards to the same tree. No content may exist in one repo and not the other after this procedure.
- The `sync` branch is infrastructure: never push it to `public`, never delete it, and never merge `sync` into `main` (that would drag legacy history into the public repo's ancestry).
- CI results are analysed on the public repo via checks: every failed job must be diagnosed, fixed on `main`, re-pushed to both repos, and re-verified green before it counts as tested.
